## 1. 目标

兑现 M3.12 三层流水数据地基的回报：**"Redis 扣了但 DB 无单"从静默差异变成定时发现、自动补偿、
有告警的闭环**。覆盖原 M5.1（比对+PENDING 扫描）与 M5.2（差异补偿+回滚失败表+告警）。

## 2. 主题内子任务

1. 定时比对：SCAN 全部活动流水 key → 逐笔核对 DB（trace_id 索引）
2. PENDING 翻牌：一致链路的订单与流水行 reconciliation_status 1→4；已恢复（logType=2）流水的恢复行同翻
3. 差异补偿：过宽限期仍无 DB 行 → 复用统一回滚入口退资格（逆增量+流水翻恢复+DB 恢复行，幂等）
4. 回滚失败表重试：删旧行重走统一入口——成功收敛（无新行），失败自动回表；行龄超阈值 error 告警人工介入

## 3. 设计取舍

- **单向比对（Redis→DB），不做反向**：Redis 是活账本（TTL 跟随活动、只存最新态），差异的唯一危险形态是
  "Redis 扣了但 DB 无单"（用户资格被占死）；"DB 有单 Redis 无流水"不构成正确性风险（缓存性质态）——
  对账资源花在会疼的地方
- **宽限期只保护差异判定，不挡一致翻牌（测试现场暴露的设计缺陷）**：初版宽限期内整笔跳过，导致刚建单的
  一致链路也翻不了牌；修正后"DB 有行"随到随翻（无害确认），仅"DB 无行"时等宽限期（建单在途，宁晚勿误）
- **补偿=复用统一回滚入口**（rollbackSeckillQualification, source=RECONCILE）：不新写补偿逻辑——
  逆增量 Lua+流水翻恢复+恢复行全套已幂等可重试，对账只是第三个触发者（前两个：请求发送失败/消费失败）。
  orderId 以 traceId 顶替落账（消息全丢场景无 orderId，traceId 雪花数值合法，DB NOT NULL 约束的占位）
- **失败表重试的"删旧走新"**：先删旧行再调统一入口——成功即收敛（Lua"无需补偿"不落新行）；失败则入口
  自动落新行回表。代价：attempts 计数在持续失败时重置，上限语义弱化为"行龄告警"（24h 仍在=人工介入信号）。
  教学取舍：行为可讲清，避免为保留计数在回滚入口上开参数口子
- **告警口径 = error 日志 + 差异状态落库**（reconciliation_status=3 预留、detail 留痕 source）：通知渠道
  （钉钉/邮件）属 M7-B 交付域，本主题把"该告警什么"的结构先立住
- **fixedDelay 而非 cron/fixedRate**：上一轮跑完再计时，天然防重叠（单实例口径；多实例需分布式锁，任务卡声明）

## 5. 验证记录（2026-09-22 本机实测）

主题 4/4；全 reactor **221/221**（217 基线 + 4），BUILD SUCCESS。

**关键断言**：seckill 成功链路 runOnce 后订单与扣减行均翻 4；手工构造"Redis 已扣+ts 回拨 5min+DB 无行"
→ runOnce 库存回/出集合/流水翻恢复 + 恢复行落库（order_id=traceId、detail 含 RECONCILE）+ 二次 runOnce
零动作零双写；ts=now 的同构差异被宽限期保护不动账；失败表行（用户已出集合）重试一轮即删除收敛。

**排障记录**：宽限期误伤一致翻牌（取舍第 2 条，测试暴露后修正语义）——"保护性延迟"应该只作用于
有副作用的判定，不该作用于无害的确认，这条对一切后台任务通用。

## 6. 学习清单

**核心知识点**
1. **对账三问**：跟谁比（相邻两层账本）、比什么（只有"单向占有型差异"要紧）、多久比一次（间隔=差异存活上限）
2. **补偿的复用**：对账不是新补偿逻辑，是既有补偿链的第三个触发者——好的补偿设计天然支持多方触发（幂等）
3. **宽限期的正确作用域**：只保护有副作用的判定（回滚资格），不挡无害的确认（翻牌一致）——延迟要有代价意识
4. **失败重试的收敛语义**：重试成功=行消失；重试失败=行回表；行龄=人工介入信号。三态清晰比计数精确更重要
5. **fixedDelay 防重叠**：最朴素的并发防护——跑完再计时，不需要锁

**面试必问题**
1. "消息丢了怎么发现？"——Redis 流水（Lua 同原子落账）vs DB 流水行（建单事务同写）：过宽限期无行即丢，
   对账任务定时比对；追问"为什么 Redis 流水可信"→与扣减同脚本原子（M3.12 的账本原子性）
2. "发现了怎么处理？"——退资格（逆增量+翻流水+恢复行，幂等可重试），用户可重抢；补偿失败落失败表等重试
3. "宽限期干什么用？"——异步建单在途的假阳性防护；讲"只保护判定不挡确认"的修正故事
4. "对账任务自己挂了怎么办？"——fixedDelay 防重叠；行龄告警兜人工；差异不会丢（Redis 流水 TTL 跟随活动）
