## 2. 设计取舍

- **user 单表合并，不拆 user/user_info/user_phone**：参考项目拆三表是为了用户按 user_id 分片后保留手机号反查能力；本项目 M4 只分片订单域（architecture.md §6），用户表永不分片，拆分只产生无意义的 1:1 join。合并后登录/资料查询单表完成
- **voucher / seckill_voucher 1:1 拆分**：普通券没有库存/时间窗语义，合并会让半数行字段为空；秒杀库存是热点行，独立表隔离"券面查询"与"库存写入"，M3.6 预热与乐观锁演进只碰扩展表
- **主键一律雪花 BIGINT，禁 AUTO_INCREMENT**：M4 分片后自增失效；M1 用 MyBatis-Plus ASSIGN_ID（内置雪花），M4 无缝切自研 id-starter，业务代码零改动
- **DATETIME 而非 TIMESTAMP**：2038 上限 + 会话时区隐式转换两个坑；与架构约定的应用层 LocalDateTime 语义对齐
- **点赞建 DB 事实表（lk_post_like）**：参考项目纯 Redis 存点赞，重启即丢事实；Localink 以 DB 为事实源、ZSet 只做榜单加速。代价是点赞多一次 DB 写，演示场景可接受
- **对账/回滚失败两表随 M1.1 一次设计、M1.2 一次建齐**：结构由秒杀链路目标态（architecture.md §4）推导，已收敛；提前定稿让 M3.12/M5.2 只写 DML 不动 DDL，避免迭代中途改表
- **路由表延后到 M4.3**：路由表结构完全由分片键决定，分片键取舍是 M4.3 的核心议题，现在设计属于超前设计（违反最小迭代原则）
- **签到/UV/订阅/Top买家/Feed/GEO 不建表**：读写形态天然是 Redis 结构，建表只引入双写一致性问题；各场景恢复策略已逐条写入 database.md 第 7 节
- **秒杀等级门槛用 min_level 单阈值，不用 allowed_levels 白名单**：演示场景只需"≥某等级"；单阈值无解析成本，人群圈选一个 `>=` 完成
- **不建物理外键**：分库分表后跨片外键不可行；约束前移应用层 + 唯一索引兜底，从 M1 养成习惯

## 5. 学习清单

**核心知识点**
1. 分库分表对表设计的反向约束：为什么"未来要分片的表"从第一天就不能用自增 ID、物理外键、跨表事务——设计是为演进路径服务的
2. 垂直拆表判据：1:1 拆分（voucher/seckill）隔离热点行与空字段；1:N 拆分判据是访问频率差异
3. 事实源与加速层的分工：DB 表 vs Redis 结构怎么选——看"丢了能否重算"与"读写形态是否天然匹配 Redis 数据结构"
4. DATETIME vs TIMESTAMP 的底层差异：存储宽度、时区转换时机、范围上限
5. 冗余计数字段（liked/comments/viewed、fans/followee）的一致性代价：写放大换读性能，接受非实时精确

**面试必问题**
1. "你的表是怎么设计的？"——按域划分 12 张表，订单域为分片预留（雪花 ID/无外键/冗余分片键），用户域单表合并，社区域 DB 事实源 + Redis 加速
2. "为什么用户表不分表？"——分表是为扛容量与写并发，本项目热点在订单域；用户表查询走缓存，拆分只增加 join 成本
3. "点赞/关注这种高频写为什么还建表？"——DB 是事实源保障可恢复，Redis 承担排序与计数加速；纯 Redis 方案重启丢数据
4. "订单状态机怎么设计的？"——已创建/用户取消/超时关闭三态，取消与超时关闭分离（运营需要区分主动取消与系统关闭），对账状态独立字段不混入主状态
