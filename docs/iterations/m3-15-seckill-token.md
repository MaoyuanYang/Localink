## 1. 目标

架构图②④格兑现：抢购前先过令牌闸门——`POST /{voucherId}/token` 申请（@RateLimit 双维度限流，
IP 10 次/60s、用户 3 次/60s），30s TTL 一次性令牌；下单接口必带令牌，Lua 原子 GET+DEL 消费。
"要不要让他进库存扣减"再前置一层：令牌挡流量，库存与判重仍是正确性最终防线。

## 2. 设计取舍

- **令牌是流量闸门不是正确性防线**：超卖防线仍是 Lua 扣减+唯一索引+对账；令牌失效最坏结果是
  多一次申请往返。两层职责分开，谁都不越位
- **消费与扣减分离（独立 GET+DEL Lua，不并入 deduct 脚本）**：并入可省一次往返，但令牌烧了
  库存不足时"票废了没抢到"体验更差，且 deduct 脚本签名再膨胀会拖累全部既有测试；分离后
  seckill() 单参方法原样保留（测试/补偿链内部入口），新 seckill(voucherId, token) 为 Controller 唯一入口
- **覆盖式发放（重申刷新旧令牌作废）**：单用户同时至多一枚有效令牌，防令牌囤积；开抢前囤票
  无意义（30s TTL 自然过期），申请时不卡时间窗
- **不匹配也删（防猜测重放）**：伪造令牌试探会烧掉真令牌——令牌值只有用户自己知道，
  攻击者无从拿到旧值，风险可忽略而防重放收益明确（测试撞上此语义，改为先验新令牌再验旧作废）
- **申请时轻校验（券存在/秒杀类型/在架）**：防无效券刷令牌占 Redis；时间窗留给扣减层重校验
- **缺 token 参数归 PARAM_ERROR**：全局异常处理器补 MissingServletRequestParameterException 映射
  （缺参不是系统错误，500 会污染告警）

## 5. 学习清单

**核心知识点**
1. **令牌闸门模式（token-gate）**：在高成本校验（库存扣减）前插一次性凭证，把无效流量挡在最外层——
   与验证码同构："先证明你值得一次计算"
2. **一次性的三种死法**：消费（正常）、过期（TTL）、作废（重申覆盖/伪造连坐）——每条路径都要有明确语义与测试
3. **GET+DEL 必须原子**：分两条命令有并发缝隙（两请求同读同删都通过）；Lua 单命令化是最小原子单元
4. **覆盖式发放 vs 追加式**：覆盖保证"至多一枚有效"，免回收逻辑；代价是重放旧令牌会连坐新令牌（防猜测语义的代价）
5. **闸门与防线的分层**：令牌挡流量（可失效可重试），扣减防超卖（不可越位）——安全分层思想在业务链路的映射

**面试必问题**
1. "秒杀怎么防住恶意流量？"——三层：限流（申请令牌接口双维度）→ 令牌一次性（GET+DEL Lua 原子）→ 库存扣减（Lua+判重）；每层挡掉一部分，核心计算只服务有效请求
2. "令牌为什么 30 秒 TTL？"——覆盖真实抢购节奏（排队→开抢），太短反复申请（打申请接口），太长囤票占内存；重申刷新所以无损
3. "令牌丢了怎么办？"——失效只是多一次申请；强调令牌不是正确性组件（超卖防线在扣减层）
4. "GET 和 DEL 为什么要一个 Lua？"——两命令间并发窗口，两个请求同读同删都通过=令牌重复消费
