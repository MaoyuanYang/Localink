---

## 1. 目标

把"库存判定 + 一人一单判重 + 扣减"从 MySQL 行锁串行搬到 Redis 单线程 Lua 原子执行：拒绝在 Redis 层完成（削峰），DB 只承接真正成交的写。配套 cache-starter 补齐 Lua 执行能力（M3.12/3.13/3.15 复用）、库存预热三时机、DB 失败补偿。

## 2. 设计取舍

- **Lua 能力下沉 cache-starter（`RedisCache.scripts()`）**：`RedisScriptOps.execute(script, List<KeyBuild>, args...)`，key 走 KeyBuild 治理。M3.12 对账流水、M3.13 限流、M3.15 令牌全是 Lua——框架能力一次到位。备选：server 拿裸 RedisTemplate（绕过门面破坏治理）/ Redisson RScript（第二执行入口）——均否
- **Key 结构：String 库存 + Set 已购，`{voucherId}` hash tag 同槽**：Lua 多 key 要求同哈希槽（Cluster 下跨槽报错），单实例按同槽设计预留平滑演进——KeyTemplate 接口注释（M2.2）早已为此埋了 `{%s}` 语法
- **扣减 Lua 返回码 0/1/2/3（成功/未预热/库存不足/重复）**：Java 侧映射 10004/10005/SYSTEM_ERROR——错误码语义与 M3.1 一脉相承；未预热抛系统错误由启动回灌兜底，**懒加载回源刻意不做**（属 M3.11/M3.12 对账体系的正式课题，参考项目也是在回滚/对账成型后才补）
- **回滚用逆增量（INCRBY +1 + SREM）而非 DEL 回源**：参考项目的回滚 Lua 是 DEL 库存 key 让下次请求回源重建——前提是有懒加载；我们没有回源时 DEL 等于全挂。逆增量幂等可重试（SISMEMBER 守卫防重复补偿）。补偿失败只 log.error，差异留 M3.12 对账
- **TTL 由每次扣减刷新为 now→endTime**：活动结束两 key 自动清理，不需要后台任务；预热时也设初值
- **预热三时机，永远以 DB 当前值为准覆盖**：①创建钩子（事务内最后一步）②启动 ApplicationRunner 回灌 endTime 未到的全部券（学 BloomInitializer 模式，兜住 Redis 丢 key/手工改库/重启一切漂移）③运营更新时重灌。已购 Set 不在预热范围内（运行时事实，重建即丢）。备选"懒加载回源"见上
- **@ServiceLock 退役（演进叙事转折点）**：M3.5 的用户维度锁是纯 DB 时代的答案；Lua 单线程原子执行让"判重+扣减"天然无缝，锁反而多余（每请求省 2~3 次 Redis 往返）。requireStock/requireFirstOrder 同步移出热路径。**DB 侧保留 CAS + 条件唯一索引双兜底**（Redis/DB 短暂不一致时的防线）——三层防线演进为：Lua（热路径权威）→ CAS → 唯一索引
- **校验链（存在/类型/上架/时间窗/等级）保留 DB 读**：刻意留白——演进叙事是"校验链逐代前移"（M3.13 限流、M3.15 令牌继续把它往前推），本迭代不动它以隔离变量。实验数据证明这不是当前瓶颈的主要矛盾

|---|---|---|---|

**exp3-redis：400 用户充足库存全成功（M3.8 动机锚点）**

| 指标 | B1 纯 DB 基线 | M3.6 |
|---|---|---|
| QPS | 88.8 | **74.9** |

**成功路径反而略变慢**——诚实归因：胜者请求多了 Lua 往返，且校验 SELECT 与事务分两次借还连接池（各等一次 Hikari=10 的队），写库仍同步逐单。**M3.6 的收益在拒绝路径（削峰）与正确性；成功路径的解绑必须靠 M3.8 把建单搬出请求线程（Kafka 异步）**。此组数据即下一迭代的动机锚点。

## 5. 学习清单

**核心知识点**
1. **Lua 原子性的来源**：Redis 单线程执行脚本，脚本内多条命令天然不可分割——不需要锁，因为"别人根本没机会插进来"。这是与"分布式锁串行化"（让并发者排队）相反的思路（消除并发本身）
2. **hash tag 与 Cluster**：`{voucherId}` 让相关 key 落同一槽位，Lua 多 key 才能在 Cluster 执行；单实例提前按此设计是免费的演进保险
3. **预热/回源/对账三种一致性策略**：预热（写时同步）最简单；懒回源（读时重建）需防重建风暴（锁+双检）；对账（事后校验）是最后防线。本批做预热+启动回灌，回源与对账属 M3.11/M3.12——参考项目三者齐全，演进路线可对照
4. **逆增量 vs DEL 回滚**：回滚方案的选型依赖"有没有回源机制"——工程方案没有真空中的最优，只有与体系配套的最优
5. **削峰的本质**：把"参与竞争的请求"和"需要落库的请求"解耦——200 个失败者只花 1 次 Redis 往返（~113ms 含 HTTP/校验），DB 只见 100 个胜者
6. **性能归因方法**：exp3 的"变慢"不是退化信号，是把瓶颈定位从"写串行"转移到"同步建单+连接池"的工具——优化前先让瓶颈显形

**面试必问题**
1. "为什么 Lua 能解决超卖？"——Redis 单线程执行脚本不可分割：判定+扣减+登记一个原子单元，并发请求串行执行脚本；对比 DB 行锁（串行在磁盘事务层）与分布式锁（串行在应用层）
2. "预热什么时候做？Redis 挂了怎么办？"——三时机（创建/启动/更新）以 DB 为准覆盖；本批未预热→系统错误+启动回灌兜底，懒回源与对账是 M3.11/M3.12 的题
3. "Redis 扣了 DB 写失败怎么办？"——逆向补偿 Lua（INCRBY+SREM，幂等）；补偿失败 log+对账兜底；对比 DEL 回源方案的适用前提
4. "加了 Lua 之后为什么还保留 CAS 和唯一索引？"——Redis 与 DB 是两个系统，存在短暂不一致窗口；Lua 是热路径权威，CAS 拦数字超卖，索引拦重复单——纵深防御各司其职
5. "锁被你删了？那一人一单靠什么？"——Lua 的 SISMEMBER+SADD 与扣减同脚本原子，判重无缝可依赖；M3.5 的锁是 DB 时代答案，被更原生的方案取代（能讲清"为什么以前要、现在不要"就是演进式开发的满分答案）
6. "压测提升了多少？瓶颈在哪？"——拒绝路径 20 倍（2345→113ms）+ QPS 102 vs 88.8；成功路径 74.9 暴露新瓶颈：同步建单+连接池——M3.8 异步化的动机
