## 1. 目标

还清 M2.10 的最后一笔已知债：多实例部署时 Caffeine 本地缓存（L1）的跨实例一致性——一家实例更新了商户，其他实例的 L1 副本要同步撕页。MQ 框架（M3.7）的第二个用户，"广播型消费组"首次登场。

## 2. 设计取舍

- **广播的实现 = 每实例独立消费组**：Kafka 按"组"投递——同组竞争消费（一条消息组内只归一人），异组全量复制。消费组名带 `${random.uuid}`（Spring 属性占位符，每个上下文解析出新值）→ 每实例自成一组 → 都收到全部失效消息。**同一个 topic，组策略决定它是工作队列还是广播**——这是 M3.9 的核心认知，与 seckill-order（固定组名，工作队列）形成同框架内的对照组
- **新实例跳过历史消息**：随机组 + 全局 `earliest` 会让新组重放保留期内全部历史失效消息（多为无效空踢）。@KafkaListener 的 `properties = {"auto.offset.reset:latest"}` 只为该 listener 覆盖——新组从最新开始。这个"listener 级配置覆盖"是收窄配置影响面的常用手段
- **消费者按 Registry 派发，不绑定 shop**：`localCacheRegistry.cache(msg.cache()).invalidate(msg.key())`——通用失效通道，未来任何本地缓存注册别名即接入；**未知别名警告跳过（ack）**：缓存下线场景属"永久不可处理"，按 M3.7 闸门语义跳过而非无限重投（重投也永远处理不了）
- **发送侧 fire-and-forget（sendAsync）**：失效广播的价值是"把最坏 10s 的脏读窗口缩到毫秒级"，是优化不是正确性依赖——L1 的 TTL 本就是兜底（M2.10 设计原话）。异步发失败留日志即可，不值得为它上重试
- **本实例同步失效保留**：更新路径仍先踢自己的 L1（立即可见），广播负责其他实例；广播回到自己时幂等再踢一次，无害
- **topic 分区数 1**：失效消息轻量、key 之间互不相干（各自踢各自），单分区每组的单消费者串行足够——分区数按用途定，与 seckill-order 的 3 分区对照

## 5. 学习清单

**核心知识点**
1. **消费组语义的两种形态**：固定组名=工作队列（负载分摊、每消息处理一次），随机组名=广播（每实例全量）。同一 topic、同一框架，组策略不同形态不同——选型不是选中间件而是选消费拓扑
2. **本地缓存一致性的三板斧**：TTL 短过期（最终一致兜底）、广播失效（主动收敛）、接受短暂脏读（业务容忍度）。三板斧的组合比追求"强一致本地缓存"现实——本地缓存的存在本身就以牺牲一致性换速度
3. **失效操作的幂等性红利**：踢一个不存在的 key 是 no-op——所以广播可重复、可乱序、可丢失（有 TTL 兜底），消息可靠性要求从"至少一次"降到"尽力而为"，整条链路无需重试/去重/顺序保证
4. **listener 级配置覆盖**：@KafkaListener 的 properties 属性只影响该监听器，与全局配置形成分层——避免为一个特例改全局
5. **"永久不可处理"与"暂时失败"的分野**：未知缓存别名重试一万次也不会成功（闸门跳过），DB 抖动重试可能成功（rethrow 重投）——错误处理策略要看错误的可恢复性

**面试必问题**
1. "多实例部署本地缓存怎么保持一致？"——TTL 兜底 + MQ 广播失效 + 业务容忍短暂脏读；能说出"本地缓存天然是最终一致"的定位
2. "Kafka 怎么实现广播？"——消费组机制：组间全量复制、组内竞争；随机组名=每实例一组
3. "失效消息丢了怎么办？"——最坏情况退化到 TTL 过期（10s 脏读窗口），失效广播是优化不是正确性依赖——按消息的业务角色定可靠性等级
4. "为什么失效不要求顺序和去重？"——踢缓存幂等，重复/乱序都是 no-op；不是所有消息都值得上恰好一次
5. "收到未知缓存的失效消息怎么处理？"——跳过（永久不可处理），别无限重投——对比"暂时失败才重投"的判断标准
