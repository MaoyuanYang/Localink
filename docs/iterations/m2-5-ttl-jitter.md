## 1. 目标

按铁律②"先暴露问题→再解决问题"：先在 Redis 侧把已回填的一批商户 key 用 `PEXPIRE` 统一改成同一时刻过期（模拟 M2.3 固定 30 分钟 TTL 在批量回填后的集体到期瞬间），过期后循环请求 20 个 id，以 MySQL `Com_select` 计数为实证，暴露雪崩问题（20 个 key 同时失效 → 20 次请求全部砸库）；随后在 `detail` 的两处缓存写入点落地**TTL 随机抖动**：正缓存与空值缓存的 TTL 均从固定值改为"基础值 + 随机增量"，批量写入的同类 key 过期时刻自然错开，集体到期的雪崩通道被消除。

涉及表：`lk_shop`（无变更）；涉及接口：`GET /api/shop/{id}`（对外行为完全不变，变化仅在写入 Redis 的 TTL 数值）；涉及 Redis Key：复用 `lk:shop:info:{id}`（**不新增 key**，仅 TTL 从固定 1800s/120s 变为随机区间）。

## 2. 设计取舍

- **抖动公式选"基础值 + 单向随机增量"，不做 ± 双向抖动**：正缓存 `30min + 随机[0, 10min)` → TTL ∈ [1800, 2400) 秒；空值缓存 `2min + 随机[0, 30s)` → [120, 150) 秒。单向加保证最小缓存时长不打折——正缓存至少仍是 30 分钟，命中率不因抖动下降，内存代价仅是多留最多 10 分钟；双向 ± 抖动会让一半 key 提前于基础值过期，缓存时长打折，而错峰效果与单向加无实质差异。抖动率 ≈33%（10min/30min）取业界惯例区间（10%~50%）的中位：太小则批量回填的 key 仍挤在窄窗口内先后过期，错峰不彻底；太大则平均缓存时长抬升、内存占用上浮
- **抖动逻辑放调用方私有实现，不下沉 cache-starter**：兑现 M2.3 在 KeyManage 登记的伏笔——"旁路缓存的 TTL 不是 key 的固有属性，M2.5 雪崩抖动时调用方传随机 TTL"。私有常量 `SHOP_CACHE_TTL`/`SHOP_NULL_CACHE_TTL` 与新增抖动常量 `SHOP_CACHE_TTL_JITTER`/`SHOP_NULL_TTL_JITTER` 同处 `ShopServiceImpl` 集中管理，加一个私有方法 `jittered(base, jitter)` 统一计算。备选否决：cache-starter `RedisStringOps.set` 增加 `set(key, value, ttl, jitter)` 重载——当前全项目仅商户旁路缓存一个抖动场景，框架 API 先行扩张违背铁律③最小迭代；等 M2.10 双层缓存等第二个抖动场景出现再评估下沉，届时组件的"为什么存在"才可解释
- **随机源选 `ThreadLocalRandom`，不注入 Bean**：JDK 自带、多线程下无竞争开销；抖动是纯计算行为，无需测试替换随机源——测试用区间断言（TTL 落在 [1800, 2400)）+ 批量 distinct 断言（多个 key 的 TTL 不全相同）从外部观测随机性，不 mock
- **空值缓存 TTL 同迭代叠加抖动**：M2.4 空值 key 由 miss 请求驱动写入——"随机 id 扫射"会在同一时刻批量写入一批空值 key，固定 2 分钟 TTL 意味着 2 分钟后集体过期、二次穿透（M2.4 学习清单预告的遗留点）。与正缓存同用 `jittered()` 方法，改造成本一个常量 + 一处调用，顺手封掉该通道
- **KeyManage.SHOP_INFO 仅更新 desc**：登记契约（template、无默认 TTL）不变——TTL 本就是调用方显式传入，抖动只是传入值的变化，Key 治理层无感知；desc 补注抖动区间供后续接手人查阅
- **实验用 `PEXPIRE` 构造"同时到期"，不等真实 30 分钟**：雪崩的前提是"批量回填 + 固定 TTL"——修复前 jar 的固定 TTL 下，真实等待 30 分钟可观察到集体过期，但演示不可接受。把已回填 key 的过期时间统一改到 3 秒后是等价加速：模拟的就是"批量同时到期瞬间"，过期后的请求行为（全部查库）与真实雪崩完全一致。修复后 TTL 天然分散（TTL 命令直接观测分布），“同时到期"时刻不复存在，无需也无法再用 PEXPIRE 构造

读链路时序：`GET /api/shop/{id}` → `GET lk:shop:info:{id}`（raw）→ `null` → 查库：存在 → toVO → `SET key {vo JSON} EX {1800 + 随机[0,600)}` → 返回；不存在 → `SET key "" EX {120 + 随机[0,30)}` → 抛 NOT_FOUND → `""` → 空值命中，不查库，直接抛 NOT_FOUND → 非空 → `RedisJsonCodec.deserialize(raw, ShopVO.class)` 直返。

写链路时序：不变——`PUT /api/shop` 先更库再删缓存；`DELETE /api/shop/{id}` 先删库再删缓存。

## 5. 学习清单

**核心知识点**
1. 缓存雪崩的两大成因：① **大量 key 同时过期**——批量预热/一波 miss 集中回填 + 固定 TTL，到期瞬间流量集体砸库（本迭代解法：TTL 随机抖动错峰）；② **Redis 实例宕机**——整个缓存层消失，所有流量全部打到库（解法：多级缓存/集群高可用，M2.10 Caffeine 双层缓存是其中一环）。M2.5 只针对成因①——抖动解决不了宕机，宕机时 key 根本不是"过期"而是"无处可查"
2. TTL 抖动为什么有效：把"N 个 key 的到期时刻"从同一个点摊开成一个窗口（本例 20 个 key 从 7 秒挤成一片 → 摊开到 430 秒），单位时间内穿透到库的请求数从 N 降到 N/窗口——数据库压力峰值被削平，这正是"错峰"的本质
3. 抖动方向选单向加（base + [0, max)）而非双向（base ± max/2）：单向加保证**最小缓存时长 = base 不打折**，命中率不因抖动下降，代价仅是平均驻留时间上浮 max/2；双向抖动让一半 key 提前过期，缓存时长打折，而错峰效果（摊开成窗口）与单向加完全等价——同等收益下单向加没有副作用
4. 抖动幅度怎么定：业界惯例 base 的 10%~50%。太小 → 摊开的窗口窄，高峰期单位时间穿透数仍然偏高；太大 → 平均缓存驻留时间抬升，内存占用与脏数据窗口同步变大。本例 30min 基数取 10min（≈33%）：20 个 key 摊开 10 分钟，每秒到期数 ≈2/60，对 DB 无感
5. 空值缓存也要抖动：空值 key 由 miss 请求驱动写入，"随机 id 扫射"会在同一时刻批量写入一批空值 key——固定 2 分钟 TTL 意味着 2 分钟后集体过期、二次穿透。凡"批量写入 + 固定 TTL"的模式都自带同刻到期隐患，抖动要加在所有批量写入路径上
6. `PEXPIRE` 实验法：不等真实 30 分钟，把已回填 key 统一 `PEXPIRE` 到 3 秒后过期，等价加速构造"批量同时到期瞬间"——过期后的请求行为（全部查库）与真实雪崩完全一致。实验设计的关键是**保留问题的因果链（批量回填→同刻到期→集体穿透），只压缩时间尺度**
7. 随机源选 `ThreadLocalRandom`：JDK 自带、无 CAS 竞争（`Random` 全局锁）、无 Bean 注入必要——抖动是纯计算行为。测试不 mock 随机源，改从外部观测：区间断言（落 [1800,2400)）+ 批量 distinct 断言（N 个 key TTL 不全相同），全同概率 (1/600)^5 ≈ 1e-14，不引入 flaky

**面试必问题**
1. "什么是缓存雪崩？怎么解决？"——两种成因分开答：大量 key 同时过期 → TTL 加随机抖动错峰（本项目：30min+[0,10min)），配合多级缓存兜底；Redis 宕机 → Redis 集群高可用（哨兵/集群）+ 服务熔断降级 + 本地缓存（Caffeine）承接。能报出自己实测数据（20 key 从 7s 挤成一片摊开到 430s、Com_select 差值 +21）是加分项
2. "TTL 抖动的幅度怎么定？为什么不用 ± 双向抖动？"——幅度取基数 10%~50%，权衡"错峰窗口宽度"与"平均驻留时间"；单向加保证最小 TTL 不打折（命中率不降），双向让一半 key 提前过期，错峰效果却相同——同等收益选无副作用的方案
3. "TTL 抖动能解决 Redis 宕机型雪崩吗？"——不能。宕机时请求根本到不了"查 TTL 过期"这一步，是缓存层整体不可用。解法是高可用集群 + 熔断降级 + 本地缓存兜底。区分两类成因是这道题的考点
4. "穿透、击穿、雪崩分别怎么防？"（体系收尾）——穿透：参数校验/空值缓存（M2.4）/布隆（M2.8）；击穿：热点 key 过期瞬间互斥锁重建（M2.6）或逻辑过期异步重建（M2.7）；雪崩：TTL 随机抖动（M2.5）+ 多级缓存/集群高可用（M2.10）。三者组合拳是完整缓存防护体系，Localink 按演进顺序逐个落地并实证
5. "你怎么验证'批量过期不再同刻发生'？"——直接观测 Redis：回填 N 个 key 后逐个 `TTL`，修复前全部相同（固定 1800），修复后互不相同且落抖动区间；配合批量回填单测断言 distinct ≥ 2 进 CI。用可观测的分布差异代替"相信代码里有 random"
